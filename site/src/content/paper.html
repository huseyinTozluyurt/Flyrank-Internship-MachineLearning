Abstract

Can a few observable page signals rank pages so that an editor's 50-page review list holds more pages carrying a supplied decline label than the existing "stale and high-traffic" rule, for clients the model has never seen? Using FlyRank's anonymized starter dataset (30,000 pages, 32 clients), I compared that rule with logistic regression and random forest on six features, over 20 repeated client-held-out splits, with leakage checks and two sensitivity analyses. Both models beat the rule: Precision@50 was 0.77 and 0.75 against 0.66 (held-out base rate 0.58), and average precision 0.66 and 0.68 against 0.58. But only the random forest kept its top-50 precision (0.77, base rate 0.55) once 1,205 pages whose missing position data almost always means a new label were removed. The output is a review queue with plain reason codes for human editors: exploratory ranking of a supplied current label, not an early-warning system and not evidence that editing improves performance.

1. The problem

An editor can review roughly 50 pages per cycle. Which 50? Today's rule says: pages not updated for more than 180 days, with the most impressions first. It is simple and transparent, but it uses two fields and ignores position and click-through rate.

This study asks whether combining a few more signals ranks pages carrying FlyRank's supplied decline label (trend_direction = down: last-30-day impressions more than 20% below the previous 30 days) higher than the rule does. The test uses clients the model has never seen, because that is how a queue would be used for a new site. The unit is one page within one client. The output is a rank, and the editor decides what, if anything, to do.

2. Data

The anonymized FlyRank content-refresh starter slice: 30,000 pages, 44 columns, 32 pseudonymized clients, trailing-90-day metrics. It contains no client names, URLs, titles or queries. 54.2% of pages carry the decline label, so every precision number on this page must be read against a base rate of about 55–58%.

Excluded on purpose: trend_direction and trend_pct (the label is computed from them), every last-30/previous-30-day window column (the label arithmetic itself), and the pseudonymous IDs (used only for grouping). Word-count and keyword fields were left out for heavy, type-dependent missingness.

3. Methodology

  • Features (6): days since last update, content age, 90-day impressions, average position (0 recoded to missing), CTR, and staleness × position.
  • Baseline: the existing stale + traffic rule, scored on the same held-out rows.
  • Models: class-balanced logistic regression and a shallow random forest (200 trees, depth 5). Median imputation plus missing-value indicators, fitted inside each training split.
  • Validation: 20 repeated 75/25 splits that hold out whole clients (about 8 per split). A random page split is run only as a diagnostic.
  • Leakage checks: an assertion blocks label-derived fields and IDs. Alone, each allowed feature ranks the label with AUC 0.51–0.59; the forbidden trend_pct scores 1.0.
  • Two risks found and tested: (1) impressions, CTR and position are measured over a 90-day window that contains the 30-day label window; an age-only model shows what survives without them. (2) The 1,205 pages with no position data are 96% labeled new, so "position missing" is a near-mechanical marker of a non-decline label; a second run drops those pages.

The forest's Precision@50 was higher than logistic regression's in 18 of 20 splits. Logistic regression's strongest signal was the missing-position flag, which mostly says "this page is new". It helps pooled metrics but does little to order the remaining pages. The capstone therefore makes random forest the default queue, reversing the earlier milestone choice.

Random page splits flatter the models

When pages are split at random, 31 of 32 clients appear in both training and test data. The forest then scores 0.85 Precision@50 and 0.73 average precision, against 0.72 and 0.66 on the same seeds when clients are held out. A random split answers "does it work on more pages from sites it already knows?", which is not the question.

5. Limitations and honest framing

  • Current label only. The label marks pages already down. Nothing here shows the system can warn before a decline.
  • Feature windows overlap the label window. Impressions, CTR and position include the label's 30 days, so part of their signal may reflect the decline itself. Feature dates cannot be verified in this snapshot; that needs the dated warehouse release, which this study did not run.
  • Only 32 clients, very uneven. Results swing with which clients are held out. The 20 splits overlap, so spreads are descriptive, not significance tests.
  • Scores are ranks, not probabilities. Class weighting shifts them (Brier 0.23, against 0.25 for a constant guess).
  • Reason codes are threshold rules on observed fields, not causes and not explanations of an individual score.
  • No outcomes measured. Nothing here shows that reviewing or editing a queued page changes its performance.

6. Ranked recommendations

  1. Use the random-forest queue as the default review list, with the logistic queue as a comparison. Each page is scored only by models that never saw its client. Expect about three in four of the top 50 to carry the decline label, against a base rate of about 55–58%.
  2. Work the top 20, then the next 30, using reason codes as a checklist. High visibility (33 of the top 50): confirm the traffic drop is real. Position band 6–22 (7): check the results page and competing pages. Model priority, context first (11): no simple flag fired, so start from context.
  3. Check context before acting: seasonality, indexing and technical health, search intent, accuracy, and whether the page should stay live.
  4. Spread review across clients. The forest's top 50 came from 6 clients, 40% from one. Cap pages per client or run the queue per client.
  5. Never bulk-edit, delete or redirect from the queue. Log what was reviewed and done, so outcomes can be measured later.

Next steps: validate on the dated DuckDB warehouse with per-client windows; if the history allows, run a true early-warning study (features from an earlier window, outcome from a later one, time-ordered validation); log editor actions so impact can eventually be measured.

7. Reproducibility

Everything on this page comes from one notebook run, work/notebooks/capstone.ipynb. It writes the metrics receipt work/outputs/capstone_metrics.json. The full write-up is work/capstone_report.md.

Rerun from a fresh clone with pip install -r requirements.txt jupyter, then jupyter nbconvert --to notebook --execute work/notebooks/capstone.ipynb, or use the notebook's Colab badge. Seeds: grouped splits 42–61 (42–46 reproduce Milestone 4); review queue built with 5 grouped splits at seed 42. Recorded with scikit-learn 1.9.1, pandas 3.0.5 and numpy 2.5.3.
